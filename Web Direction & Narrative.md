# AI Decision System Website — Direction & Narrative

## Core Goal

This website is NOT a generic AI SaaS landing page.

It should feel like:

- an operational systems product
- a runtime execution engine
- a structured business decision platform

Target audiences:

1. AI Forward Engineer / Solution Engineer interviewers
2. Technical directors / architects
3. Future business stakeholders / CEOs

The website should balance:

- business readability
- operational realism
- systems thinking
- technical depth

WITHOUT becoming:

- overly abstract
- AI buzzword-heavy
- graph-flexing
- architecture-porn
- generic "AI agent" marketing

---

# Narrative Direction

The website should feel like:

"Business operations become harder as systems, policies, and approvals grow together."

NOT:

"We invented revolutionary AI."

The tone should be:

- grounded
- operational
- realistic
- systems-oriented
- calm
- structured

Avoid overusing words like:

- autonomous
- revolutionary
- AGI
- intelligent orchestration
- cutting-edge
- next-generation

Avoid sounding like:

- startup hype
- infra worship
- Palantir cosplay

---

# Overview Page Responsibilities

Overview page is NOT architecture deep dive.

It should answer:

1. Why operational complexity grows
2. Why execution becomes difficult
3. What kind of problems this system solves
4. High-level lifecycle:
   - Interpret
   - Plan
   - Decide
   - Execute
5. What use cases the structure supports

Overview should:

- create intuition
- create operational resonance
- feel readable
- have breathing room

NOT:

- explain ontology deeply
- explain implementation details
- show complex graphs
- dump technical concepts

---

# Hero Section Direction

Hero RIGHT SIDE should NOT show:

- abstract graph
- ontology topology
- dependency DAG

because business users cannot understand it immediately.

Instead:

show an operational scenario projection.

Example:

Refund Request
↓
VIP Customer
↓
Coupon Already Used
↓
Shipping Already Dispatched
↓
Manager Approval

with floating runtime states like:

- Policy Updated
- Approval Required

This creates:

- business readability
- technical implication
- operational realism

Background can contain:

- subtle grid
- subtle atmosphere
- subtle nodes

ONLY as atmosphere.

NOT as the main semantic payload.

---

# Trace Line Direction

Trace lines should:

- move the story forward
- act like chapter transitions
- be short
- be understandable instantly

Good examples:

- WHERE DO THESE OPERATIONAL PROBLEMS COME FROM?
- HOW THE SYSTEM HANDLES THESE PROBLEMS.

Avoid:

- abstract enterprise language
- vague AI wording
- overly long transitions

---

# Challenge Section Direction

Operational challenges should be:

- grounded
- realistic
- conversational
- operational

NOT:

- generic enterprise buzzwords

Good direction:

Business:
"We just need one extra refund rule."

Engineering:
- Which VIP definition?
- Which policy version?
- Does shipping affect eligibility?
- Should coupon recovery apply?

This creates:

- operational tension
- realism
- resonance

Challenge tabs should map to lifecycle stages:

- Intent Parsing
- Planning
- Policy Coordination
- Traceability

Each challenge can use different UI styles.

---

# Lifecycle Section Direction

Lifecycle should be:

Interpret → Plan → Decide → Execute

This is the high-level system narrative.

NOT:

ontology → graph → DAG → executor

Avoid implementation-first explanations on Overview page.

---

# Use Cases Direction

Use cases should emphasize:

"One structure, support multiple use cases."

Preferred use cases:

- Order Assistant
- AI Marketing
- Workflow Automation

Avoid low-ROI examples like:

- pure risk review
- abstract compliance demos

Use cases should feel:

- operational
- commercially meaningful
- easy to understand

---

# CTA Direction

CTA should be:

short
clear
navigation-oriented

Preferred:

"Explore how they work in Architecture"

NOT:

"Want to see the full end-to-end execution flow?"

because it is too verbose.

---

# Visual Direction

Target feeling:

- Linear
- Stripe
- Apple
- modern infrastructure product

BUT:

more operational
less abstract

Use:

- subtle grids
- breathing room
- progressive disclosure
- restrained colors
- calm hierarchy

Avoid:

- overloading graphs
- over-animating
- giant neon AI visuals
- too many icons
- cyberpunk aesthetics

---

# Frontend Architecture Direction

Keep frontend simple.

Do NOT overengineer semantic frontend architecture yet.

Preferred structure:

- UI sections in:
  app/.../_components/

- content in:
  content/overview/
  content/architecture/
  content/evolution/

Avoid:

- ContentHero
- SectionHero
- semantic frontend ontology systems

Current priority:

clarity > theoretical purity

---

# Most Important Principle

The website should feel like:

"Someone who deeply understands operational systems."

NOT:

"Someone trying to impress people with AI concepts."
